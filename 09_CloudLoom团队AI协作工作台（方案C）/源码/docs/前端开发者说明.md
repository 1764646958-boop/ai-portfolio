## 一、项目结构

### 1.1 仓库根目录


### 1.2 后端模块职责一览表

后端为 Express 薄代理层，进程入口 `server/src/index.js`，监听 `127.0.0.1:8787`（API + MCP），
另起一个 Express 实例在 `127.0.0.1:3000` 托管前端静态（生产环境实际由 Caddy 直出 `dist`，3000 为兜底）。
全部文件位于 `/opt/team-console/server/src/`：

| 文件 | 行数 | 职责 |
|---|---|---|
| `index.js` | 61 | 进程入口。挂载 `/api/*` 各模块与 `/mcp`；`/api/health`；启动 `tasks.recoverStale({boot:true})` + `tasks.startSweeper()`；`lazy.initTable()` 后每 5 分钟 `lazy.sweep` |
| `config.js` | 60 | 全部常量与路径；`.env` 极简解析（密钥只进 `.env`）；`JWT_SECRET` 缺失时 `process.exit(1)` 拒绝启动 |
| `db.js` | 53 | `data/conversations.db`（`node:sqlite`，WAL）：`users` / `conversations` / `conversation_members` / `messages` 四表建表 |
| `util.js` | 64 | `nowIso` / `uuid` / `genKey` / scrypt 口令散列与校验 / 原子写 JSON / 文件锁 `acquireLock` / 文件名与分类净化 / `isValidProfileId` |
| `registry.js` | 58 | `agents.json` 读写（每次读盘）+ 端口预分配 8650–8999 + 文件锁防竞态；4 预设 Agent 的中文名/职责 `PRESET_META` |
| `lazystart.js` | 110 | 懒启动进程管理：探活 / 拉起 / 60s 超时 / 空闲 30min 停止 / 5min 巡检 / 实例运行表（详见第四节） |
| `auth.js` | 125 | 注册、登录、`/me`、成员列表、批准、停用；JWT `httpOnly`+`Secure` Cookie（S4.0/B3）；导出 `authRequired` / `adminRequired` / `publicUser` |
| `chat.js` | 103 | `POST /api/chat`：按 `agents.json` 路由 + Bearer 注入 + SSE 透传 + 懒启动 `status` 事件；导出非流式 `callAgent`（被 kanban/tasks/conversations 复用） |
| `conversations.js` | 172 | 私聊/群聊会话与消息；增量拉取（`since` seq）；`@Agent` 异步拉入（N4 方案 A：system 注入最近 24h/20 条）；5 分钟撤回 |
| `kanban.js` | 43 | `GET /api/kanban` 只读查 SQLite 共享看板（含评论）；`POST /api/kanban-command` 把自然语言指令转成给值班 Agent 的聊天消息 |
| `files.js` | 108 | 资料库：`≤10MB` 上传（`multer` memoryStorage）/ 网盘外链 / 列表检索 / 下载 / 删除（管理员）。含 multipart 中文文件名双重编码修复 |
| `poll.js` | 32 | `GET /api/poll`：读 `系统通知/` 目录，按文件 `mtime` 增量返回；供前端 3–5s 轮询（D19） |
| `profiles.js` | 87 | `GET /api/profiles`：读 `系统通知/画像/*.json`，**后端**按请求者 ACL 过滤（普通成员只见本人条目，管理员全见） |
| `tasks.js` | 563 | 办公任务中心（D23/D35/D36）：建表（tasks / task_corrections / outputs）、队列单飞执行器 `pump`、D36 敏感词强制人审、审批三动作、产物扫描、60s 巡检、任务完成沉淀记忆 |
| `memories.js` | 262 | 团队共享记忆库（D24/D25）：`data/team-memory.db` + FTS5(trigram，可降级 unicode61) + LIKE 兜底；ACL `private|team|restricted`；导出 `insertMemory` / `searchMemories` / `precipitateTaskMemory` |
| `mcp.js` | 163 | MCP 网关（D28，Streamable HTTP）：`POST /mcp` JSON-RPC 2.0，5 个工具 `kanban_list` / `file_search` / `memory_search` / `memory_add` / `task_create`；Bearer 复用工作台 JWT |

## 二、代理层接口文档

### 2.1 读取方法

下表由 `grep -n "router\.(get|post|put|delete)" /opt/team-console/server/src/*.js` 逐条核对源码得到（源码正则中的转义符在此省略），**共 43 条**。

- 所有 `/api/*` 路由挂载在 `index.js:17-28`；MCP 挂载在 `index.js:37`。
- 未匹配任何 `/api/*` 路由时统一返回 `404 { error: "接口不存在" }`（`index.js:39`）。
- 错误统一由 `index.js:41-45` 的兜底中间件返回 `{ error }`；**前端 `api.ts` 依赖该字段**（见第三节）。

**「需登录」列含义**：
`✔` = 挂了 `authRequired`（JWT Cookie 或 `Authorization: Bearer`，见 `auth.js:22-38`）；
`管理员` = 额外挂了 `adminRequired`（`auth.js:39-42`）；
`✘` = 匿名可访问。

## 三、前端如何调用后端

### 3.1 fetch 封装：`src/api.ts`

前端**只有一个** HTTP 出口：`api<T>(path, options)`（`src/api.ts:2-11`），它做四件事：

1. 统一拼前缀 `/api`（同源，无跨域、无 baseURL 配置）；
2. `credentials: 'same-origin'` —— 带上 `tc_token` Cookie（见 3.2）；
3. `body` 是 `FormData` 时**不设** `Content-Type`（交给浏览器生成 multipart boundary），否则设 `application/json`；
4. 非 2xx 时抛出 `new Error(data.error || "请求失败 " + status)` —— 与后端 `{ error }` 约定配对（`index.js:41-45`）。
   注意：错误**统一是 Error.message**，视图层普遍用 `catch (e) { err.value = e.message }`。

`sender 侧`所有调用都长这样（任务、记忆、资料库、看板、Agent 一致）：

```ts
const r = await api<{ tasks: Task[] }>('/tasks?limit=200')
await api('/tasks', { method: 'POST', body: JSON.stringify(form.value) })
const up = await api<{ file: { name: string } }>('/files', { method: 'POST', body: fd })   // FormData 分支
```

MCP 端点 `/mcp` **不经过** `api()`（前端不直接调 MCP；MCP 供外部客户端使用）。

### 3.2 token 存储方式：httpOnly Cookie，前端不接触
> **S4.0/B3 变更**：Cookie 增加 `secure: true`、登录响应体不再含 `token`。本节及本文其它处引用的 `auth.js:NN` 行号，
> 因该次改动插入了 3 行注释，登录后的行号整体 +2~+4（本次已校准 §3.2 与接口表 3/6 行，其余行号未逐一重排）。

- 后端登录/注册成功后 `setCookie()` 下发 **httpOnly Cookie**：键名 `tc_token`（`config.js:44`），
  属性 `httpOnly: true; sameSite: 'lax'; secure: true; maxAge: 7 天; path: '/'`（`auth.js:17-19`，S4.0/B3 补 `Secure`）。
- **前端 JS 永远读不到也写不到这个 token**（全局铁律 4：前端不接触任何密钥）。
  `src/` 内不存在任何 `localStorage` / `sessionStorage` / `document.cookie` 存取 token 的代码。
- 前端只持有**用户信息对象**：Pinia `useAuthStore` 的 `state.user`（内存态，刷新即丢）：
  - `fetchMe()` → `GET /api/me`，失败置 `null`（`stores/auth.ts:12-16`）；
  - `login()` → `POST /api/login` 后写入 `this.user`（`stores/auth.ts:17-20`）；
  - `logout()` → `POST /api/logout` 后清空（`stores/auth.ts:26`）。
- 登录守卫在 `router.ts:24-29` 的 `beforeEach`：首次进入先 `fetchMe()`，未登录一律跳 `login`。
- **Bearer 通道**：后端 `extractToken()`（`auth.js:22-26`）优先取 `Authorization: Bearer <JWT>`，
  其次取 Cookie。这就是 MCP 外部客户端复用工作台 JWT 的方式；`POST /api/login` 响应里的
  `token` 字段即为此准备（`auth.js:76`）。前端自身不使用该字段。

### 3.3 SSE 流式聊天接入

SSE 消费器是 `chatStream()`（`src/api.ts:21-73`），只在 **Agent 直聊模式** 使用：

```ts
await chatStream({ agent: id, messages: history }, { onStatus, onDelta, onError, onDone }, signal?)
```

调用链：`ChatView.vue:50`（`sendToAgent`）→ `api.ts` 的 `chatStream` → `POST /api/chat`（`stream:true`）。

**协议约定（前后端逐字对齐）**：

| SSE 事件 | 载荷 | 前端处理 |
|---|---|---|
| （无 event，`data:`） | OpenAI 分片 `{ choices:[{ delta:{ content } }] }` | 追加到气泡（`api.ts:62-66`） |
| `data: [DONE]` | 字面量 | 收流结束（`api.ts:61`） |
| `event: status` | `{ status:"waking" / "ready", message }` | 写入 `status.value`，界面显示「正在唤醒 …」（`api.ts:59`） |
| `event: error` | `{ error }` | 气泡替换为 `⚠️ …` 并结束（`api.ts:60`） |

**关键实现细节**：

- 前端用 `res.body.getReader()` + `TextDecoder` **手动切分**：以空行（两个换行）为一条事件边界，
  块内 `event:` 取事件名、`data:` 可多行并以换行拼接（`api.ts:48-58`）。这与后端 `sseWrite()`
  的 `event: X\n data: Y\n\n` 输出格式（`chat.js:33-36`）严格对应。
- 后端在 SSE 开始时先写一行 `: ok` 注释帧（`chat.js:55`）用于尽早建立连接，前端对该帧无 `data:` 会直接跳过。
- **M1 无状态约束**：每次请求都必须携带**完整会话历史**。`ChatView.vue:47-49` 每次发送前把本地消息
  重新映射为 `{ role: 'user' | 'assistant', content }` 数组（过滤掉正在生成的占位消息），
  前端**不自建会话 id**——Agent 直聊历史只存在浏览器 IndexedDB（键 `agent:<id>`，`ChatView.vue:26/66`）。
- 中断：`AbortController` 的 `signal` 由调用方传入；读取异常时 `AbortError` 被静默忽略（`api.ts:70`）。

### 3.4 轮询机制（SPEC 禁止 WebSocket，一律轮询）

SPEC §三明确「没有 WebSocket 事件流」，D19 定 3–5 秒轮询。源码共 **5 处** 定时器：

| 位置 | 间隔 | 干什么 |
|---|---|---|
| `lib/notify.ts:72`（由 `main.ts:10` 以 **4000ms** 启动） | 4s | `GET /api/poll?since=<上次 now>`，新通知入列表 + 桌面 Notification |
| `views/ChatView.vue:93` | 4s | `chat.loadConvs()` + 当前会话增量 `chat.pull()` |
| `views/TasksView.vue:161` | 5s | `GET /api/tasks?limit=200` + 刷新当前任务详情 |
| `views/KanbanView.vue:77` | 8s | `GET /api/kanban` 重载看板 |
| `components/SideBar.vue:45` | 8s | `chat.loadConvs()` 刷新未读红点 |

**`/api/poll` 的增量语义**（`poll.js:11-30` + `notify.ts:52-65`）：

1. 前端维护模块级变量 `since`（初始 0），每轮以 `GET /api/poll?since=<since>` 请求；
2. 后端只返回 `mtime > since` 的**文件**（`画像/` 子目录被显式排除，由画像 Tab 单独读）；
3. 响应回带服务端 `now`，前端把它赋回 `since`（**用服务端时钟，避免前端时钟漂移漏读**）；
4. **首轮只建基线不弹窗**（`primed` 标志，`notify.ts:57`）——避免登录瞬间把历史通知全部轰炸出来；
5. 通知列表内存态上限 50 条；桌面通知只对最近 3 条弹（`notify.ts:45`），且尊重
   `user.notify_enabled` 开关（`notify.ts:43-44`，该开关经 `PUT /api/me` 持久化）；
6. 登出时 `resetNotify()` 重置 `since` 与 `primed`（`MainLayout.vue:25`），避免换账号串号。

### 3.5 本地缓存：IndexedDB（不替代服务端）

`src/lib/idb.ts` 提供 `idbLoad/idbSave/idbClear`，库名 `cloudloom`、对象仓 `conv`：

- 会话模式：`ChatView`/`chat store` 打开会话时**先读缓存秒出**，再用服务端结果校正
  （`stores/chat.ts:62-76`）；消息合并规则 `merge()`：服务端为权威，本地 `pending`（乐观回显）保留在末尾（`stores/chat.ts:79-86`）；
- Agent 直聊：历史以 `agent:<id>` 为键存 IndexedDB（`ChatView.vue:26/66`）；
- 隐私模式等 IndexedDB 不可用时**静默降级**，不影响主流程（`idb.ts:29`）。

## 四、懒启动机制（`server/src/lazystart.js`，SPEC 4.2 / D5 / C3）

### 4.1 设计目标

4 个预设 Agent（`cehua` / `chengxu` / `pingshen` / `zhiban`）由 systemd **常驻**；
管理员自建的 Agent **不常驻**，按需拉起、空闲 30 分钟自动停止——既省 2核4G 的内存，又保证成员无感知。

### 4.2 实例运行表（内存态）

`lazystart.js:8` 维护 `instances: Map<profileId, Instance>`：

```
{ port, running, managed: 'systemd' | 'lazy', lastActive, starting: Promise | null }
```

- `managed` 的判定：`preset ? 'systemd' : 'lazy'`（`lazystart.js:14`）——**只有自建 Agent 会被空闲回收**。
- `table()`（`lazystart.js:10-20`）每次调用都重新 `readRegistry()`（即重读 `agents.json`），
  因此管理员新建的 Agent 无需重启代理层即可被纳入管理；同时把注册表里的最新端口同步进内存表。

### 4.3 探活：`probe(port, timeoutMs)`

- 请求 `GET http://127.0.0.1:<port>/health`，用 `AbortController` 控制超时，
  默认 **1500ms**（`config.js:47` `PROBE_TIMEOUT_MS`），异常一律视为「未运行」（`lazystart.js:22-29`）。
- `isRunning(id)` = `probe(实例端口)`（`lazystart.js:31-35`）。

### 4.4 拉起：`ensureRunning(id)`（`lazystart.js:47-71`）

调用顺序与边界条件（**这是本节最关键的流程**）：

1. 查注册表：Agent 不存在 → 抛 `code='NO_AGENT'`；`enabled === false` → 抛 `code='DISABLED'`；
2. 先 `probe`：**已在跑** → 刷新 `lastActive` 并返回 `{ woke: false }`（零开销）；
3. **并发合并**：若该 Agent 已有进行中的 `starting` Promise，直接返回同一个 Promise
   （`lazystart.js:55`）——防止多人同时发消息把同一个实例拉起多次；
4. 否则执行 `hermes -p <id> gateway start`（`runCmd`，`execFile` `HERMES_BIN`，超时 **30s**，`lazystart.js:37-44 / 58`）；
5. 然后**每秒轮询一次 `/health`**，直到 **60s 上限**（`START_TIMEOUT_MS`，`config.js:48`）：
   - 就绪 → `running = true`、刷新 `lastActive`，返回 `{ woke: true }`；
   - 超时 → 抛 `Error("Agent 启动失败，请管理员检查（60s 内 /health 未就绪）")`；
6. 无论成败，`.finally()` 清空 `starting`（`lazystart.js:68`）。
7. **失败不静默重试**：错误向上抛，由 `chat.js` 转成 SSE `error` 事件或 403/502 JSON。

`touch(id)`（`lazystart.js:73-76`）在每次成功转发后刷新 `lastActive`——调用点在
`chat.js:26`（非流式）与 `chat.js:92`（SSE 透传成功后）。

### 4.5 空闲回收与巡检：`sweep()`

- 由 `index.js:61` 以 `setInterval(lazy.sweep, C.SWEEP_INTERVAL_MS)` 触发，**每 5 分钟**一次
  （`SWEEP_INTERVAL_MS`，`config.js:50`）。
- 每轮：① 对**所有**实例重新探活并写回 `running`；② 仅当 `managed === 'lazy'`
  且 `now - lastActive > IDLE_STOP_MS`（**30 分钟**，`config.js:49`）时，执行
  `hermes -p <id> gateway stop`（超时 30s）并置 `running = false`（`lazystart.js:85-91`）。
- 预设 Agent 的 `managed = 'systemd'`，**永不被 sweep 停止**；停不掉时只记错误日志，不影响其他实例。

### 4.6 启动初始化：`initTable()`

`index.js:61` 在进程启动时 `await lazy.initTable()`：建表 + 对全部实例探活一次，
把已在跑者（如 systemd 常驻的 4 预设）的 `lastActive` 置为当前时间，并打印
`[lazystart] 实例表初始化: cehua:up chengxu:up ...`（`lazystart.js:96-103`）。

### 4.7 端口预分配（8650–8999，M4 文件锁防竞态）

- 常量：`CUSTOM_PORT_MIN = 8650`、`CUSTOM_PORT_MAX = 8999`（`config.js:51-52`）。
- `allocatePort(reg)`（`registry.js:52-56`）从 8650 起取**第一个未被注册表占用**的端口；
  池耗尽时抛 `端口池耗尽（8650-8999）`。
- 分配与写 `agents.json` 在**同一个文件锁事务**内完成（`updateRegistry` → `acquireLock(C.REGISTRY_LOCK)`，
  `registry.js:37-50`），因此并发创建多个 Agent 不会撞端口。
- 4 个预设的端口是固定的：`cehua 8642 / chengxu 8643 / pingshen 8644 / zhiban 8645`（实测 `agents.json`）。
- 自建 Agent 的 systemd 单元以 `gateway install --system --run-as-user root
  --no-start-now --no-start-on-login` 安装（`agents.js:83` 附近），**reboot 后不自动启动**，完全交由懒启动按需拉起。

### 4.8 前端如何呈现「正在唤醒」

后端（`chat.js:58-69`）：收到 `POST /api/chat` 后**先探活**；若未运行，
在 SSE 通道内先发一帧状态事件，再阻塞等待拉起：

```
event: status
data: {"status":"waking","message":"正在唤醒 策划Agent…"}
...  (ensureRunning：最多 60s)
event: status
data: {"status":"ready","message":"策划Agent 已就绪"}
```

前端链路：`api.ts:59`（解析 `status` 事件）→ `ChatView.vue:51`（`status.value = s.message`）
→ `ChatStream.vue:106-109` 渲染**蓝色脉冲圆点 + 文案**：

```html
<div v-if="status || streaming" class="flex items-center gap-2 text-xs text-gray-500">
  <span class="inline-block w-2 h-2 rounded-full bg-blue-500 animate-pulse"></span>
  <span>{{ status || '正在生成…' }}</span>
</div>
```

其他呈现点：

- `ChatView.vue:105-107` Agent 直聊头部显示 `activeAgent.status.running ? '已就绪' : '休眠中（发送即唤醒）'` + 端口号；
- `GET /api/agents` 返回每 Agent 的 `status`（来自 `lazystart.statusOf()`：`running` / `managed` / `last_active`，
  `lazystart.js:105-108`、`agents.js:45`），`SideBar.vue` 与 `SettingsView.vue` 用它渲染运行状态点；
- `stores/chat.ts:37-38` 的两个 getter `runningAgents` / `sleepingAgents` 即基于该字段。

> 因此**前端无需为懒启动写任何额外逻辑**：只要消费 `status` 事件即可，
> 60s 超时会以 `event: error` 到达，前端按 3.3 的 `onError` 显示 `⚠️ Agent 启动失败，请管理员检查…`。

**命名安全规则**（`util.js:57-60`）：`sanitizeName` 把 `/ : * ? " < > |` 与控制字符替换为 `_`，
去掉前导 `.`，空串则用 fallback；分类名额外截断到 64 字符。这是**目录穿越防护**——分类与文件名都不可能逃出 `team-files/`。

> **注意**：`画像/` 是 `系统通知/` 的**子目录**，不是 `team-files/` 的直接子目录。
> 同时 `poll.js:17` 显式跳过子目录，因此画像 JSON **不会**混进通知流（前端通知铃铛不会因画像刷新而响）。

### 5.4 产物的登记与下载（融合闭环）

1. Agent 按指令把文件写进 `产出/<task_id>/`（`tasks.js:202`）；
2. 任务收尾时 `scanOutputs(task)` **递归**遍历该目录，把未见过的文件登记进 `outputs` 表

3. 前端 `GET /api/tasks/:id` 拿到 `outputs[]`（只暴露 `id/task_id/file_name/file_size/created_at`），

4. 任务完成同时沉淀一条 `conclusion` 记忆（`memories.js:166-199`），内容含产物路径 `${OUTPUT_DIR}/${task.id}/`，
   并把产物文件后缀（如 `md`）并入记忆 tags。

### 7.2 类型检查门槛（最容易踩的坑）

`tsconfig.app.json` 开启了两条严格规则：

```json
"noUnusedLocals": true,
"noUnusedParameters": true,
"erasableSyntaxOnly": true,
"noFallthroughCasesInSwitch": true
```

含义与后果：

- **任何未使用的局部变量 → 构建失败**。典型场景：注释掉一段用到某变量的模板后忘了删 `const x = ref(...)`；
  `import` 了一个组件/类型但模板里没用到（`noUnusedLocals` 同样报错）。
- **任何未使用的函数参数 → 构建失败**。需要占位时用下划线前缀（如 `_e`）或直接删掉参数。
- `vue-tsc -b` 是 `&&` 的**前件**：类型检查不过，`vite build` 根本不执行，`dist/` 保持旧版本——
  此时**页面看起来「没更新」但其实是没构建成功**，务必看终端输出。
- 检查范围是 `src/**/*.ts`、`src/**/*.tsx`、`src/**/*.vue`。
  注意 `src/views/TasksView.vue.bak-share`（现有遗留备份文件）**不匹配**该 glob，
  因此不会被类型检查、也不会进 bundle——但它仍是仓库噪音，建议删除（本次文档任务未改动任何代码）。

### 7.3 产物如何被托管

```
浏览器 --HTTPS(:443, Caddy 自签证书)--> Caddy
                                          ├── /api/*  → reverse_proxy 127.0.0.1:8787
                                          ├── /mcp*   → reverse_proxy 127.0.0.1:8787
                                          └── 其余    → root /opt/team-console/team-console/dist
                                                        header /manifest.webmanifest → application/manifest+json
                                                        try_files {path} /index.html   # SPA fallback
                                                        file_server
```

- 权威托管是 **Caddy `file_server`**（配置 `/etc/caddy/Caddyfile`，站点块 `:443`，TLS 用自签证书，
  域名备案就绪后把 `:443` 改成 `<域名>` 并删掉两行 `tls` 即可自动签发正式证书——见 Caddyfile 头部注释）。
- `server/src/index.js:50-58` 另起一个 Express 静态服务在 `127.0.0.1:3000` 托管同一个 `dist`，
  作为兜底（`STATIC_PORT`，`config.js:40`）；`dist` 缺失时返回 503「前端尚未构建」。
  **生产流量不走 3000**，改前端无需重启后端。
- **改前端不需要重启 `team-console` 服务**（Caddy 直接读磁盘文件）；改**后端**才需要
  `systemctl restart team-console`。

### 7.4 重新构建与发布（标准流程）

这就是「本地开发调试」的核心约束，也是 §8.2 两种做法存在的理由。

### 8.2 两种开发姿势

**姿势 A（推荐）：在服务器上跑 Vite dev server + SSH 隧道**

```bash
# 服务器侧
cd /opt/team-console/team-console && npm run dev     # 默认 5173

# 本机侧（另开终端）建立隧道
ssh -L 5173:127.0.0.1:5173 root@<服务器IP>
# 然后本机浏览器打开 http://localhost:5173
```

`vite.config.ts:6-8` 已配置 dev 代理：

```ts
server: { proxy: { '/api': 'http://127.0.0.1:8787', '/mcp': 'http://127.0.0.1:8787' } }
```

于是 dev server 与后端**同源**：Cookie 正常下发、无 CORS、**不经过 Caddy**，
因此**完全避开自签证书问题**（不用点「继续访问不安全站点」，也不会出现
`fetch` 被证书错误拦截、SSE 被中间盒缓冲等疑难）。

**姿势 B：直连后端 8787（免证书调试接口）**

`http://127.0.0.1:8787` 是**纯 HTTP、无 TLS**，是排查「到底是前端问题还是 Caddy/证书问题」的最佳入口：

```bash
# 在服务器上执行
curl -s http://127.0.0.1:8787/api/health
# {"ok":true,"service":"team-console","time":"..."}
```

从本机访问时用隧道：`ssh -L 8787:127.0.0.1:8787 root@<服务器IP>`，
再访问 `http://localhost:8787/api/health`。

> **对比**：走域名 `https://<IP>/api/health` 会命中自签证书，`curl` 需要 `-k`、浏览器需要手动信任；
> 而 8787 直连没有这个问题，且返回内容完全一致（Caddy 只是 `reverse_proxy`，不做改写）。

### 8.3 调试接口的认证方式（两种都可用）

后端 `extractToken()`（`auth.js:22-26`）**先 Bearer 后 Cookie**，所以调接口有两种姿势：

```bash
# 姿势 1：Cookie jar（模拟浏览器）
curl -s -c /tmp/cj -X POST http://127.0.0.1:8787/api/login \

#   ↑ S4.0/B3 起 /api/login 不再回传 token；MCP/外部客户端请用专用签发脚本（如 /root/mcpclient/mint.cjs）或改用 Cookie
```

> 口令与 token **只在本机临时使用**，不要写进任何文件、脚本或本文档。

### 8.6 前端侧调试要点

- **IndexedDB 缓存会「骗」你**：改了消息渲染后若显示陈旧，先清理
  浏览器 DevTools → Application → IndexedDB → `cloudloom` → `conv`（或整库删除）。
  `stores/chat.ts:62-76` 的策略是「先出缓存、再用服务端校正」，所以缓存脏数据会一闪而过。
- **PWA Service Worker 也会「骗」你**：改了 `public/` 下资源或怀疑缓存问题，
  DevTools → Application → Service Workers → Unregister，或勾选 Bypass for network。
- **SSE 断开排查**：先确认不是代理缓冲——后端已设
  `X-Accel-Buffering: no` + `Cache-Control: no-transform`（`chat.js:50-53`）；
  若经 Caddy 仍卡住，用 §8.2 姿势 B 直连 8787 对比定位。
- **登录态异常**：Cookie 是 `sameSite: 'lax'` + `secure`（`auth.js:17`）。**`secure` 意味着浏览器只在 HTTPS 下携带该 Cookie** ——
  工作台必须以 HTTPS（Caddy 443）访问；直连 `http://IP:3000` 或 `http://127.0.0.1:8787` 只能用于本机 curl 诊断，登录会「成功但保持不住」。
  另外，
  用 IP 与域名混着访问会各自持有一份 Cookie，表现为「突然要重新登录」——统一用一个入口访问。
- **`npm run preview`** 可在服务器上本地预览 `dist` 构建产物（默认 4173），验证「构建后是否正常」。
- **不要在前端引入任何密钥**：前端只与同源 `/api` 通信，`API_SERVER_KEY` 只存在于
  `agents.json` 与各 profile 的 `.env`（文件权限 600），由后端在转发时注入
  （`chat.js:22 / :84`）。
