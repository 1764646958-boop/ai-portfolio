## 1. 懒启动故障（自建 Agent）

**机制（`server/src/lazystart.js` / `chat.js`）**：聊天请求先探活 `GET http://127.0.0.1:<port>/health`（超时 1500ms）；
未就绪则发 SSE `正在唤醒 <name>…`，再执行 `hermes -p <id> gateway start`（命令超时 30s），
之后每 1s 探活一次、最长 **60s**；仍失败抛 `Agent 启动失败，请管理员检查（60s 内 /health 未就绪）`。
`preset:true` 的 4 个预设恒常驻；**只有自建 Agent**（`preset:false`）参与懒启动，空闲 **30min** 被 `sweep()` 停止（每 5min 一轮）。

| 现象 | 可能原因 | 排查命令 | 处置办法 |
|---|---|---|---|
| 1.1 一直显示「正在唤醒」 | Agent 未启动 / 冷启动慢 / 端口不通 / Agent 已停用 | 见下方 1.1 命令 | 等 30-60s；超 60s 转 1.2；页面断流则刷新 |
| 1.2 报「60s 内 /health 未就绪」 | profile `.env` 的 `API_SERVER_*` 与 `agents.json` 不一致 / 端口被占 / provider 密钥缺失 / 内存不足 | 见下方 1.2 命令 | 先对齐端口，再重启单元 |
| 1.3 Agent 起不来 | 单元未安装 / `ExecStart` 路径不存在 / venv 损坏 / 端口冲突 | 见下方 1.3 命令 | 按 1-5 步定位；重建单元属中风险 |
| 1.4 被自动停止后又唤不醒 | 空闲 30min 正常停止 / 单元进 `failed` / 端口被残留进程占住 | 见下方 1.4 命令 | 先分辨「正常停止」还是「异常退出」 |
| 1.5 端口占用冲突（8650+） | 端口池被残留 hermes / 手工实例 / 其它服务占用 | 见下方 1.5 命令 | 先定归属，再停单元或清孤儿进程 |

### 1.1 一直显示「正在唤醒」

```bash
journalctl -u team-console -n 100 --no-pager | grep -E "lazystart|tasks"   # 后端是否收到唤醒并抛错
ss -lntp "sport = :8650"                                                  # 端口是否有进程在听
curl -s -m 3 -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8650/health # 200 = 自认就绪
systemctl status hermes-gateway-testbot --no-pager -l
journalctl -u hermes-gateway-testbot -n 50 --no-pager
```

| 排查结果 | 处置 |
|---|---|
| `curl` 返回 `200` | Agent 其实已就绪，前端 SSE 已断未重连 -> 刷新页面【风险：低】 |
| 日志出现 `Agent「xxx」已停用` | 该 Agent `enabled:false`，用管理员账号在 Agent 管理里启用，或 `PUT /api/agents/<id>` 传 `{"enabled":true}`。**不要手改 `agents.json`**（有文件锁 + 原子写）【风险：低】 |
| 单元 `active (running)` 但不通 | 转 1.2 |
| 单元 `failed`/`inactive` | 转 1.3 |

### 1.3 Agent 起不来

```bash
systemctl cat hermes-gateway-testbot --no-pager                   # 看 ExecStart
ls -l /usr/local/bin/hermes /usr/local/lib/hermes-agent/venv/bin/python

```

| 排查结果 | 处置 |
|---|---|
| 无该单元 | 单元未安装，需管理员走「删除后重建」流程，**不要手写单元文件**【风险：中】 |
| 路径缺失 | Hermes 运行时被动过，先用 `systemctl --failed` 确认影响范围（**所有**网关可能一起挂）【风险：高】 |
| 日志含 `Address already in use` | 转 1.5 |
| `is-failed` 返回 `failed` | `systemctl reset-failed <unit>` 后 `systemctl start <unit>`；重启前备份该 profile 的 `SOUL.md` 与 `.env`【风险：中】 |
| 任何情况 | **禁止** `hermes -p <id> gateway run` 手工启动 —— 会与 systemd 抢同一端口（实测曾出现同一 profile 两个 PID 并存，见 附录 C-8）【风险：高】 |

### 1.4 空闲被自动停止后又唤不醒

```bash
journalctl -u team-console --since "-2 h" --no-pager | grep -E "lazystart|已停止|sweep"  # 是否被正常清扫
systemctl status hermes-gateway-testbot --no-pager -l | head -12
systemctl is-failed hermes-gateway-testbot
ss -lntp "sport = :8650"; fuser -n tcp 8650; ps -o pid,ppid,cmd -p <PID>   # 有无残留进程
```

| 排查结果 | 处置 |
|---|---|
| 有 `[lazystart] 空闲超 30min，已停止: <id>`，单元 `inactive (dead)` | **设计内行为**，在聊天里再发一条消息即可重新唤醒，无需管理员【风险：低】 |
| `is-failed` 返回 `failed` | `systemctl reset-failed hermes-gateway-testbot` 后再唤醒【风险：中】 |
| 端口有残留进程但单元已停 | 先 `ps -o pid,ppid,cmd -p <PID>` 看 PPID：**PPID=1** 说明由 systemd 托管，改用 `systemctl stop <单元>`，**不要 kill**；PPID 非 1 为手工孤儿进程，需清理并在清理前留证【风险：高】 |
| 频繁被停影响使用 | 阈值由 `team-console` 环境变量 `IDLE_STOP_MS`（毫秒）控制，属**配置变更**且需重启 `team-console` 才生效【风险：中】 |

### 1.5 端口占用冲突（8650+ 被占）

```bash
ss -lntp "sport = :8650"          # 方式 1（推荐）
fuser -n tcp 8650                 # 方式 2（最快，只给 PID）
lsof -iTCP:8650 -sTCP:LISTEN -P -n # 方式 3（信息最全）
ss -lntp | grep -E ":(86[4-9][0-9]|89[0-9][0-9]) "   # 一次扫出整个端口池占用
jq -r "to_entries[] | [.key, (.value.port|tostring), (.value.preset|tostring)] | @tsv" /opt/team-console/agents.json
ps -o pid,ppid,user,etime,cmd -p <PID>                # 占用者归属
systemctl status <PID> --no-pager                     # 直接问 systemd 它属于哪个单元（已核对可用）
cat /proc/<PID>/cgroup                                # 最权威：如 /system.slice/hermes-gateway-testbot.service
```

| 排查结果 | 处置 |
|---|---|
| 占用者就是注册表里登记的 Agent | 正常，无需处理 |
| 占用者是**其它** systemd 托管的 hermes 单元 | `systemctl stop <单元名>` 释放端口后再唤醒目标 Agent【风险：中】 |
| 手工孤儿进程（PPID 非 1） | 先 `ps` 记录 PID/命令行留证，再 `kill <PID>`；无效才 `kill -9`。**执行前必须逐个比对 `systemctl status <单元> \| grep "Main PID"`，确认它不是任何单元的 MainPID**【风险：高】 |
| 新建 Agent 分到了被占端口 | **已知设计缺口**：`allocatePort()` 只查 `agents.json`，不查主机实际占用，见 附录 C-2 |

## 2. 任务失败 / 卡住 / 排队 / 审批 / 产物

**状态机**：`queued` -> `running` -> `done` / `waiting_approval` / `failed`。同 Agent **单飞**（同时只跑 1 个），单任务执行上限 `TASK_TIMEOUT_MS = 600s`。
`waiting_approval` 由敏感词规则触发（**金额**：金额/预算/报价/费用/成本/定价/价格/付款/支付/发票/万元/合同额；**对外承诺**：对外/承诺/合同/签约/客户/甲方/乙方/发布/公告/公开/上线通知；**删除数据**：删除/清除/销毁/清空/卸载/覆盖/drop/delete/truncate；例外「客户端」不算「客户」），或低置信且值班复核不可用时被强制转人工。

> **`sqlite3` CLI 在本机未安装（已核对）**。库查询一律用 Node 内置 `node:sqlite` 的**只读**模式（模板见 [8.2](#82-只读查看推荐方式)），或走 `/api/*`。**不要**安装 sqlite3、**不要**直接写库。

| 现象 | 可能原因 | 排查命令 | 处置办法 |
|---|---|---|---|
| 2.1 `status=failed`，看不到原因 | 原因在 `tasks.error` / `result_summary`，列表接口不展开 | 见 2.1 | 按 error 文案分流；重新发起任务，**不要改库** |
| 2.2 卡在 `running` | 执行器被重启打断（孤儿任务）/ Agent 长时间不返回 | 见 2.2 | 巡检 1 分钟内自愈；必要时走取消接口 |
| 2.3 一直 `queued` | 前序任务占位（最长 600s）/ 执行器未推进 | 见 2.3 | 看 `queue_ahead`；必要时取消前序任务 |
| 2.4 `waiting_approval` 不交付 | 命中敏感词 / 低置信且复核不可用 | 见 2.4 | 由创建者或管理员调审批接口 |
| 2.5 产物目录为空 / 下载 404 | Agent 未写入约定目录 / 扫描只在完成时做一次 / `oid` 传错 | 见 2.5 | 先确认磁盘有无文件，再判断「未写」还是「未登记」 |

### 2.1 status=failed（如何看 error）

```bash
node -e 'const{DatabaseSync}=require("node:sqlite");const d=new DatabaseSync("/opt/team-console/data/tasks.db",{readOnly:true});console.log(JSON.stringify(d.prepare("SELECT id,agent_id,status,progress,error,result_summary,completed_at FROM tasks WHERE status=? ORDER BY created_at DESC LIMIT 10").all("failed"),null,1));d.close()'

# 走 API（需登录 Cookie，密码静默输入，勿写入命令历史/文档/聊天记录）
read -r -p "用户名: " TCUSER; read -rsp "密码: " TCPW; echo
jq -n --arg u "$TCUSER" --arg p "$TCPW" '{username:$u,password:$p}' > /tmp/tc-login.json
curl -sk -c /tmp/tc.cookie -X POST https://127.0.0.1/api/login -H "Content-Type: application/json" --data @/tmp/tc-login.json
rm -f /tmp/tc-login.json; unset TCPW
curl -sk -b /tmp/tc.cookie "https://127.0.0.1/api/tasks?status=failed"
curl -sk -b /tmp/tc.cookie "https://127.0.0.1/api/tasks/<TASK_ID>"   # 含 queue_ahead / outputs / corrections
```

| `error` 文案特征 | 含义 | 处置 |
|---|---|---|
| `Agent 声明无法完成：<原因>` | Agent 自判做不了（多为任务描述缺输入） | 补齐描述 / 引用资料后重新发起 |
| `值班复核未通过：<原因>` | 低置信交付被 zhiban 驳回 | 看 `result_summary` 里的原回复，修正后重跑 |
| `Agent 执行超时（超过 600 秒未返回）` | 超过 `TASK_TIMEOUT_MS` | 拆分任务；调大超时属**配置变更**（需重启）【风险：中】 |
| `执行失败：上游 <port> 返回 <code>` | Agent 网关异常 | 转[第 1 章](#1-懒启动故障自建-agent) |
| `执行失败：Agent 返回空回复` | 上游 200 但内容为空 | 用 1.1 的 `curl` 直连该端口复现 |
| `指令组装失败` / `执行异常` | 代码或数据异常 | 带 `journalctl -u team-console` 原文交管理员 |

### 2.2 任务卡在 running

```bash
journalctl -u team-console --since "-30 min" --no-pager | grep -E "中断恢复|孤儿任务自动重排|巡检异常|tasks"
node -e 'const{DatabaseSync}=require("node:sqlite");const d=new DatabaseSync("/opt/team-console/data/tasks.db",{readOnly:true});console.log(JSON.stringify(d.prepare("SELECT id,agent_id,status,progress,started_at,created_at FROM tasks WHERE status=?").all("running"),null,1));d.close()'
ss -lntp "sport = :8645"; curl -s -m 3 -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8645/health
```

**自愈机制**：`recoverOrphans()` 每 **60s** 判定一次 —— DB 标 `running` 但**本进程内未执行**的即为孤儿，立即改回 `queued`（`progress` = `执行中断，自动重排`）；
服务重启时 `recoverStale({boot:true})` 用 **30s** 宽限回收上一进程遗留的 `running`（`progress` = `执行中断，重新排队`，日志 `[tasks] 中断恢复：N 个任务重新排队`）。

| 排查结果 | 处置 |
|---|---|
| 日志有 `中断恢复` / `孤儿任务自动重排` | 正常自愈，等 1 分钟即可，**无需人工** |
| 对应 Agent 不健康（第 3 条命令非 200） | 先修 Agent（[第 1 章](#1-懒启动故障自建-agent)），任务随队列自动继续 |
| 想主动终止 | `POST /api/tasks/<id>/cancel`（置 `failed`，仅创建者或管理员）。取消不可撤销且不沉淀记忆，执行前确认确实不需要结果【风险：中】 |
| 任何情况 | **严禁** `UPDATE tasks SET status=...` 解卡 —— 库里一致性依赖执行器的单飞集合，手改会造成双执行或状态与产物不一致。人工干预只能走 `/api/tasks/<id>/cancel`【风险：高】 |

### 2.3 任务一直 queued（排队）

**`POST /api/tasks/<id>/approval` 三种动作的结果**

| `action` | 结果 | 说明 |
|---|---|---|
| `approve` | `done` / `approval_status=approved` / 记录 `approved_by` | 交付并沉淀记忆 |
| `modify` | `queued` / `approval_status=modified` / 写 `correction_note` | 带修正意见**返工**，重新排队执行 |
| `reject` | `failed` / `approval_status=rejected` / `error` 写驳回理由 | 直接失败，不交付 |

| 返回 | 原因 | 处置 |
|---|---|---|
| `403 仅任务创建者或管理员可审批` | 当前账号权限不足 | 换创建者或管理员账号 |
| `400 任务当前状态为 <x>，不可审批` | 任务已不是 `waiting_approval` | 刷新列表看最新状态 |
| `400 note 必填（审批意见/修正理由）` | 漏传 `note` | 补上 `note` |
| `400 action 须为 approve\|modify\|reject` | 动作拼写错 | 用上表三个取值 |

## 3. 通知不弹

**链路（`src/lib/notify.ts` + `main.ts`）**：`/root/team-files/系统通知/` 下的文件 -> 前端每 **4000ms** 调 `GET /api/poll?since=<ms>`（需登录 Cookie）-> 更新 `notifyList` / `unread` -> `pushDesktop()` 弹桌面通知（受 `users.notify_enabled` 门控）。
`registerSW()` 在 `window load` 时注册 `/sw.js`（失败静默忽略，不影响主流程但 PWA 离线能力失效）。轮询**只扫顶层文件**，`画像/` 子目录不进通知流。

| 前置条件（缺一不可） | 说明 | 验证 |
|---|---|---|
| ① 安全上下文 | 必须 **HTTPS 且证书受浏览器信任**。当前是 `:443` **自签证书**降级路径：未把 `cloudloom.crt` 导入信任库时浏览器视该源为不安全，`Notification` 不可用且 SW 注册失败 | 控制台 `window.isSecureContext` 须为 `true` |
| ② 通知权限 | `Notification.permission` 须为 `granted`；`denied` 后 JS **无法再申请** | 控制台 `Notification.permission` |
| ③ Service Worker | `/sw.js` 可访问且 MIME 为 JS | 控制台 `navigator.serviceWorker.getRegistrations()` |
| ④ 服务端开关 | `users.notify_enabled = 1` | 下方命令 3 |

> **iOS 特例**：iOS Safari 普通标签页 `Notification` 为 `undefined`，须先「添加到主屏幕」并以 PWA 打开（iOS 16.4+）。


| 现象 | 可能原因 | 处置办法 |
|---|---|---|
| 完全无弹窗，控制台无报错 | 证书不受信任 -> `isSecureContext=false` / `Notification` 未定义 | 【风险：低】把 `/etc/caddy/certs/cloudloom.crt` 导入客户端信任库；或走备案域名 + 正式证书 |
| `permission` 为 `denied` | 曾点「阻止」或被全局禁止 | 【风险：低】浏览器地址栏站点设置里手动改回「允许」（JS 已无法再申请） |
| 权限 granted、开关也开，仍不弹 | `users.notify_enabled=0`（前端读 `auth.user.notify_enabled`） | 【风险：低】「设置」Tab 打开开关（`PUT /api/me` 持久化），或重新登录刷新用户对象 |
| 角标在涨但不弹桌面 | 系统勿扰/专注模式拦截 | 【风险：低】关闭勿扰；用「设置」Tab 的「发送测试通知」验证链路 |
| 一条都不弹，`/api/poll` 返回 401 | 未登录 / Cookie 过期 | 【风险：低】重新登录（见[第 6 章](#6-认证与登录)） |
| PWA 装不上 / 离线不可用 | SW 注册失败（多为证书不受信任） | 先满足前置条件 ①，再反注册 + 硬刷新 |
| 新文件已生成但角标不动 | 文件写进了子目录（如 `画像/`），不进通知流 | 【风险：低】属设计如此，子目录内容由「画像」Tab 单独读取 |

> **已知缺陷（首次登录会「炸历史」）**：`main.ts` 在应用启动（含登录页）时就调用 `startNotify(4000)`，而登录页阶段 `/api/poll` 必然 401；
> `tick()` 把 `primed = true` 写在 `try/catch` **之外**，失败时 `since` 仍为 `0` 但 `primed` 已被置位；
> 且 `resetNotify()` **只在退出登录时**调用。结果：**先看到登录页再登录**的用户，登录后第一次成功轮询会以 `since=0` 拉回
> `系统通知/` 下**全部历史文件**，未读角标直接等于历史文件数，并弹出最多 3 条旧文件的桌面通知（随使用时间恶化）。
> 线上日志确有 `401 /api/poll?since=0` 佐证。详见 附录 C-3。

### 5.2 Caddy 配置校验与重载

```bash
caddy version                                          # 当前 2.6.2（2.6 无 default_sni，故用 :443 而非 IP 站点）
caddy validate --config /etc/caddy/Caddyfile           # 校验语法，不改配置；期望末行 Valid configuration
caddy fmt /etc/caddy/Caddyfile                         # 只打印到 stdout，不写回文件
systemctl reload caddy                                 # 平滑重载（SIGUSR1），加载失败则保留旧配置继续服务
systemctl restart caddy                                # 仅在 reload 不生效时用，会瞬断连接
journalctl -u caddy -n 50 --no-pager
ls -la /var/log/caddy/; tail -n 20 /var/log/caddy/cloudloom-access.log
```

| 动作 | 风险 | 前置备份 / 说明 |
|---|---|---|
| `caddy validate` / `caddy fmt` | 低 | 只读，不改文件 |
| `systemctl reload caddy` | 中 | 不断流；改配置前先备份 `Caddyfile` 与 `/etc/caddy/certs/` |
| `systemctl restart caddy` | 中 | 瞬断 443 上所有连接（含进行中的 SSE），**低峰期**执行 |
| 修改 `Caddyfile` | 高 | 必须先 `validate` 通过再 `reload`；配置错误时 `reload` 会被拒（旧配置继续跑），但 `restart` 会**启动失败** |

**Caddy 关键事实**：① 站点是 `:443` 端口站点（RFC 6066 禁止 SNI 为 IP 字面量，Caddy 2.6 无 `default_sni`），**不要**改成 `https://<服务器IP>`；
② 证书自签（CN 含 `CloudLoom Session0 (self-signed, IP-only degraded path)`，SAN 含 `<服务器IP>`/`127.0.0.1`/`localhost`/`<域名>`），**有效期至 2028-12-16**；
③ 同时监听 80 并自动 301/308 跳转到 443；④ 显式声明 `manifest.webmanifest` 的 MIME 为 `application/manifest+json`（否则浏览器拒绝解析 manifest，PWA/SW 场景会失败）。

### 5.3 team-console 的日志到底在哪看

**结论（已核对）：`team-console` 只写 journald，不存在独立日志文件。** 单元里是 `StandardOutput=journal` + `StandardError=journal`，
且 `find` 确认 `/opt/team-console` 下**没有** `nohup.out` 或任何 `*.log`。任何「去找 nohup 输出」的做法在本部署上都是错的。

```bash

journalctl -u team-console -n 100 --no-pager         # 最近 100 行
journalctl -u team-console --since "-30 min" --no-pager
```

## 6. 认证与登录

**机制（`auth.js`）**：登录态是 JWT，写入 **httpOnly Cookie `tc_token`**（`sameSite=lax`、`path=/`、有效期 **7 天**），
（S4.0/B3 起）**登录响应体已不再返回 `token`**，但后端仍接受 `Authorization: Bearer`；token 需通过专用签发方式获得（如 /root/mcpclient/mint.cjs）；取 token 顺序为「先 Bearer，后 Cookie」。
口令用 `scrypt`（N=16384）散列；签名密钥为 `server/.env` 的 `JWT_SECRET`（**未配置则服务拒绝启动**）。
账号状态：`pending`（待批准）-> `active`（可登录）-> `disabled`（已停用）；**首个注册账号自动成为 admin + active**，之后注册一律 `pending`。

```bash
# 登录拿 Cookie（密码静默输入，绝不写入命令历史 / 文档 / 聊天记录）
read -r -p "用户名: " TCUSER; read -rsp "密码: " TCPW; echo
jq -n --arg u "$TCUSER" --arg p "$TCPW" '{username:$u,password:$p}' > /tmp/tc-login.json
curl -sk -i -c /tmp/tc.cookie -X POST https://127.0.0.1/api/login -H "Content-Type: application/json" --data @/tmp/tc-login.json | head -20
rm -f /tmp/tc-login.json; unset TCPW
# 期望：HTTP/2 200 + Set-Cookie: tc_token=...（值不要外泄）

curl -sk -b /tmp/tc.cookie https://127.0.0.1/api/me                    # 验证登录态
curl -sk -b /tmp/tc.cookie https://127.0.0.1/api/members                # 管理员列出全部成员
curl -sk -b /tmp/tc.cookie -X POST "https://127.0.0.1/api/members/<USER_ID>/approve"   # 批准成员（无需请求体）
curl -sk -b /tmp/tc.cookie -X POST "https://127.0.0.1/api/members/<USER_ID>/disable"   # 停用成员（不能停用自己）
curl -sk -b /tmp/tc.cookie -X POST https://127.0.0.1/api/logout         # 退出登录（清 Cookie）

# 只读直查用户表（无需登录态，不打印任何凭据）
node -e 'const{DatabaseSync}=require("node:sqlite");const d=new DatabaseSync("/opt/team-console/data/conversations.db",{readOnly:true});console.log(JSON.stringify(d.prepare("SELECT id,username,display_name,role,status,notify_enabled,created_at FROM users ORDER BY created_at").all(),null,1));d.close()'
# 找出所有非 active 账号（待批准 / 已停用）
node -e 'const{DatabaseSync}=require("node:sqlite");const d=new DatabaseSync("/opt/team-console/data/conversations.db",{readOnly:true});console.log(JSON.stringify(d.prepare("SELECT id,username,status FROM users WHERE status<>? ORDER BY created_at").all("active"),null,1));d.close()'
```

| HTTP | 文案 | 真实含义 | 处置 |
|---|---|---|---|
| 401 | `未登录` | 请求里根本没有 token | 登录；检查是否漏带 Cookie / Bearer |
| 401 | `登录态无效或已过期` | JWT 校验失败（过期 / 签名不匹配） | 重新登录。若**所有人同时**失效，多半是 `JWT_SECRET` 变了 |
| 401 | `账号不存在` | token 有效但用户行已删除 | 重新注册 / 管理员核对 |
| 403 | `账号待批准或已停用` | `status` 不是 `active` | 管理员批准（见下） |
| 401 | `用户名或密码错误` | 登录接口，用户不存在或密码错 | 用户名规则 `字母数字._-`，2-32 位 |
| 403 | `账号待管理员批准` | 登录接口，`status=pending` | 管理员 `POST /api/members/<id>/approve` |
| 403 | `账号已停用` | 登录接口，`status=disabled` | 走恢复流程或重新注册 |
| 403 | `仅管理员可操作` | 调了管理员接口但当前是 `member` | 换管理员账号 |
| 409 | `用户名已被注册` | 注册接口重名 | 换用户名 |

| 现象 | 可能原因 | 处置办法 |
|---|---|---|
| 成员注册后一直 pending | **设计如此**：除首个账号外注册一律 `pending`，必须管理员批准 | 【风险：低】管理员在成员管理界面批准，或调 `POST /api/members/<id>/approve`。**当前线上 4 个账号均已 `active`，无积压**（已核对） |
| 接口一律 401，重登后立刻又 401 | Cookie 丢失/过期；`JWT_SECRET` 被重新生成（**所有旧 token 同时失效**）；浏览器禁 Cookie | 【风险：低】固定用一个访问地址；确认 `JWT_SECRET` 未变动；用上面 curl 复现以区分浏览器侧还是服务端侧 |
| 管理员自己也登不进去 | 管理员账号被停用，或 `JWT_SECRET` 丢失 | 【风险：高】**不要**直接改库把 `status` 改成 `active`；若确属密钥丢失导致全员失效，属灾难恢复，须负责人决策后重建 `JWT_SECRET`（**会让所有人重新登录**） |

> **多地址访问会「登录串不上」**：`tc_token` **未设置 `Domain` 属性**，属主机级 Cookie。
> 用 `https://<服务器IP>` 登录后切到 `https://<域名>`（或 `http://`）会看不到登录态；`www` 与非 `www`、IP 与域名之间也不共享 Cookie。
> 团队内部应统一一个访问地址。这不是故障，是预期的同源行为。另：该 Cookie **未设 `Secure`**（见 附录 C-10）。

## 7. 上传与资料库

**机制（`files.js`）**：`POST /api/files` 为 `multipart/form-data`，文件字段名固定 **`file`**，分类字段名 `category`；
大小上限 **10 MiB**（`UPLOAD_MAX_BYTES = 10 * 1024 * 1024`，由 multer 强制）；采用 **`memoryStorage()`** —— 整份文件先进内存再落盘；
落盘到 `/root/team-files/<category>/<文件名>`（`category` 缺省 `资料库`，截断 64 字符），元数据登记在 `/opt/team-console/data/files.json`（文件锁 + 原子替换）。
文件名清洗会去掉**斜杠、反斜杠、冒号、星号、问号、双引号、尖括号、竖线与控制字符**并去掉开头圆点，重名自动加 `(1)` `(2)`。
中文名已修复（`decodeUploadName()` 还原 busboy 按 latin1 解析造成的双重编码）。其他 JSON 接口体上限为 **2MB**（`express.json`，超限 **413**）。

```bash

rm -f /tmp/big.bin
# 改用链接方式登记（不计入 10MB 限制；url 必须 http(s)://）
jq -n --arg n "大文件-网盘" --arg u "https://example.invalid/x" '{name:$n,url:$u,category:"资料库"}' > /tmp/tc-link.json
curl -sk -b /tmp/tc.cookie -X POST https://127.0.0.1/api/links -H "Content-Type: application/json" --data @/tmp/tc-link.json
rm -f /tmp/tc-link.json
# 查看与检索
curl -sk -b /tmp/tc.cookie "https://127.0.0.1/api/files?q=测试"
jq -r '.[] | [.id, .kind, .name, .category, (.size // "-"), (.path // .url // "-")] | @tsv' /opt/team-console/data/files.json
ls -la /root/team-files/资料库/ && find /root/team-files -type f -mmin -120 | head
# 下载与删除
curl -sk -b /tmp/tc.cookie -o /tmp/dl.bin -w "%{http_code} %{size_download}\n" "https://127.0.0.1/api/files/<ID>/download"
curl -sk -b /tmp/tc.cookie -X DELETE "https://127.0.0.1/api/files/<ID>"
# Caddy 层该路径真实状态码
jq -r "select(.request.uri|startswith(\"/api/files\")) | \"\(.status) \(.request.uri)\"" /var/log/caddy/cloudloom-access.log | tail -20
```

| 现象 | 可能原因 | 处置办法 |
|---|---|---|
| 上传返 `400 文件超过 10MB 上限（大文件请走网盘链接，D14）` | 文件超过 10 MiB | 【风险：低】用「添加链接」登记网盘 / 对象存储地址。**不要**为图省事调大 `UPLOAD_MAX_BYTES` —— 落盘前整份文件驻留内存，在 2C4G 上会直接加剧 OOM【风险：高】 |
| 上传返 `400 缺少文件（multipart 字段名 file）` | 字段名不是 `file` | 改字段名；curl 用 `-F "file=@路径"` |
| 上传返 `413` | 走的是 JSON 接口且体超过 2MB | 大内容改走 multipart 上传口 |
| 文件名乱码（如 `é¶æ®µ3ä¸Šä¼ .txt`） | busboy latin1 双重编码（**已修复**，仅旧数据可能残留） | 【风险：中】由管理员删除条目后重传；**不要**手工重命名磁盘文件（`files.json` 的 `path` 会失配，下载立即变 410） |
| 下载 `404 条目不存在` | `id` 传错或条目已删 | 用 `GET /api/files` 或 `jq` 重新取准确 `id` |
| 下载 `400 链接条目请直接访问 url` | 对 `kind=link` 调了下载接口 | 打开该条目返回的 `url` 字段 |
| 下载 `410 文件已不存在于磁盘` | 注册表有记录但磁盘文件被移走/删除 | 找回文件放回原 `path` 位置，或删除条目后重传 |

> **`DELETE /api/files/<id>` 风险等级：高** —— 它会 `fs.unlinkSync()` **永久删除磁盘文件**且不可撤销。
> 执行前必须：① 确认已另行备份；② 确认没有任务 / 消息引用它；③ 需要留档时先 `cp` 到 `/root/backup/`。

|---|---|---|---|

### 8.1 WAL 说明（为什么不能只拷 `.db` 文件）

三个库都以 **`journal_mode = WAL`** 打开（已实测确认）。WAL 下事务先写入 `<库名>.db-wal`，checkpoint 时才合并回主库，
因此任一时刻磁盘上有三个文件：`.db` / `.db-wal` / `.db-shm`。**实测证据**：核对时 `tasks.db` 主文件只有 **4096 字节**、
而 `tasks.db-wal` 约 **1.3 MB**，`team-memory.db-wal` 约 **2.5 MB** —— 此时直接 `cp tasks.db` 只能得到一个 4KB 空壳。

| 认知 | 正确做法 |
|---|---|
| 「数据库就是那个 `.db` 文件」 | 错，数据可能大部分还在 `-wal` 里 |
| 只 `cp` 主库文件当备份 | **错，会丢数据**，改用 [8.3](#83-备份正确姿势一致快照) 的 `backup()` |
| 手工删除 `-wal` / `-shm` | **绝对禁止**，会造成已提交事务丢失甚至库损坏 |
| WAL 文件很大是否异常 | 正常。SQLite 约每 1000 页（4KB 页 -> 约 4MB）自动 checkpoint，无需人工干预 |

### 8.2 只读查看（推荐方式）

用 Node 内置 `node:sqlite` 的 `readOnly: true` 打开，**不写、不锁库、不影响在线服务**。改 SQL 即可直接复制执行：

```bash
# 通用只读查询模板
node -e 'const{DatabaseSync}=require("node:sqlite");const d=new DatabaseSync("/opt/team-console/data/tasks.db",{readOnly:true});const q=(s,...a)=>console.log(JSON.stringify(d.prepare(s).all(...a),null,1));q("SELECT id,agent_id,status,progress,created_at FROM tasks ORDER BY created_at DESC LIMIT 10");d.close()'

# 库 / 表 / 行数总览
cat > /tmp/dbq.cjs <<'JSEOF'
const { DatabaseSync } = require('node:sqlite');
for (const f of ['conversations', 'tasks', 'team-memory']) {
  const d = new DatabaseSync('/opt/team-console/data/' + f + '.db', { readOnly: true });
  const t = d.prepare("SELECT name FROM sqlite_master WHERE type='table' ORDER BY name").all().map(r => r.name);
  console.log(f + '.db ->', t.map(n => n + ':' + d.prepare('SELECT COUNT(*) n FROM "' + n + '"').get().n).join('  '));
  d.close();

JSEOF
node /tmp/dbq.cjs; rm -f /tmp/dbq.cjs
```

> 核对时实测规模：`conversations.db` -> `users:4  conversations:2  conversation_members:4  messages:9`；
> `tasks.db` -> `tasks:17  task_corrections:4  outputs:15`；`team-memory.db` -> `memories:17` + FTS 索引表。
> 等价的 API 只读方式：`GET /api/tasks`、`/api/tasks/<id>`、`/api/members`、`/api/files`（需登录态）。
> 库文件权限核对为 `644 root:root`，root 可直接读（权限问题见 附录 C-6）。

### 8.3 备份（正确姿势：一致快照）

```bash
cat > /tmp/db-backup.cjs <<'JSEOF'
const { DatabaseSync, backup } = require('node:sqlite');
const [src, dst] = process.argv.slice(2);
(async () => {
  const db = new DatabaseSync(src, { readOnly: true });
  await backup(db, dst);
  db.close();
  console.log('backup ->', dst);
})().catch(e => { console.error('ERR:', e.message); process.exit(1); });
JSEOF
mkdir -p /root/backup
TS=$(date +%Y%m%d-%H%M%S)
for f in conversations tasks team-memory; do
  node /tmp/db-backup.cjs "/opt/team-console/data/$f.db" "/root/backup/$f-$TS.db"
done
rm -f /tmp/db-backup.cjs
ls -la /root/backup/
```

| 动作 | 风险 | 说明 |
|---|---|---|
| `backup()` 生成快照 | 低 | 只读源库；服务在写时也安全（已实测可用） |
| 备份放 `/root/backup/` | 低 | **不要**放进 `/root/team-files/`，避免混入用户文件目录 |
| 备份前停服务 | 不需要 | `backup()` 就是为在线热备设计的 |
| 用备份**恢复**线上库 | **高** | 必须先 `systemctl stop team-console`，覆盖三个库**并删除对应 `-wal`/`-shm`**，再启动；操作前先对现状再做一次备份 |

### 8.4 数据库禁止事项（务必遵守）

| 禁止 | 原因 |
|---|---|
| 手工 `UPDATE` / `DELETE` / `INSERT` 改 `tasks.status`、`users.status` | 执行器与鉴权依赖进程内状态与库状态一致，手改会造成双执行、状态错乱 |
| 删除 `*.db-wal` / `*.db-shm` | 丢失已提交事务，甚至损坏数据库 |
| 安装 `sqlite3` CLI 并直接写库 | 绕过代码里的文件锁与原子写，极易与在线服务冲突 |
| 用 `.dump` / 二进制拷贝替代 `backup()` | WAL 未 checkpoint 时会拷到不完整状态 |
| 手改 `agents.json` / `files.json` | 两者都有文件锁 + 原子替换，手改会与 `updateRegistry()` / `saveFiles()` 竞态 |

**唯一正确的数据修改路径是 HTTP API**：任务审批 / 取消、成员批准 / 停用、文件增删、Agent 管理。

### 9.2 OOM 判断方法

```bash
free -m; swapon --show; cat /proc/sys/vm/swappiness      # 1) 先看 available 而不是 free（实测 swappiness=60）
dmesg -T | grep -i -E "oom|killed process"               # 2) 内核是否真的 OOM kill 过（本次核对：0 条）
journalctl -k --since "-1 day" --no-pager | grep -i -E "oom|killed process"
systemctl status systemd-oomd                            # 3) 用户态 OOM 管家：本机 Unit ... could not be found（没有兜底）
systemd-cgtop -m -n 1 --order=memory | head -15          # 4) 按 cgroup 看谁在吃内存（比 ps 准，不含重复共享页）
for u in caddy team-console hermes-gateway-cehua hermes-gateway-chengxu hermes-gateway-pingshen hermes-gateway-zhiban hermes-gateway-testbot docker; do printf "%-30s cur=%-12s peak=%s\n" "$u" "$(systemctl show $u -p MemoryCurrent --value)" "$(systemctl show $u -p MemoryPeak --value)"; done   # 5) 单元 current / peak
ps -eo rss,user,pid,ppid,comm --sort=-rss | head -15     # 6) 按 RSS 粗排（RSS 会重复计算共享内存，仅作粗排）
systemctl show team-console -p NRestarts -p Result -p ExecMainStatus   # 7) 是否被内存杀过
```

| 观察 | 结论 | 处置 |
|---|---|---|
| `dmesg` 有 `Out of memory: Killed process <PID> (<name>)` | 确认发生内核 OOM kill | 看被杀的是谁；若是 hermes/node，按 9.3 释放内存后重启该单元 |
| `available` < 300 MB 且 swap used 持续增长 | 已进入危险区，随时可能 OOM | 立即按 9.3 处置，**先减负载再谈优化** |
| `available` 充裕但 `NRestarts` 在涨 | 不是 OOM，是进程自身崩溃 | 转[第 5 章](#5-服务与进程systemd--caddy--日志) |
| `MemoryPeak` 远高于 `MemoryCurrent` | 曾出现瞬时高峰（浏览器工具、大任务） | 记录峰值来源；评估错峰跑任务 |

> **本机没有 `systemd-oomd`，也没有任何 cgroup 内存上限**（`MemoryMax=infinity`，实测）。
> 内存耗尽时是**全局**内核 OOM killer 出手，它按 `oom_score` 挑进程 —— 很可能杀掉 `team-console` 或某个 hermes 网关，
> 而不是「最占内存」的那个。叠加 附录 C-7 的无限重启会形成「被杀 -> 重启 -> 再被杀」循环。
> 这让**预防**比事后定位重要得多（详见 附录 C-4）。

### 9.3 内存偏紧时的处置（代价由低到高）

| 序号 | 动作 | 释放量（估算） | 风险 | 执行前须确认 / 备份 |
|---|---|---|---|---|
| 1 | 停用不用的**自建** Agent（管理界面 `enabled:false`） | 约 120-160 MB / 个 | 低 | 确认没人正在用它 |
| 2 | 停掉 **docker**（本机无容器、无镜像） | 约 120 MB | 中 | 确认无人依赖本机 docker；`systemctl stop docker docker.socket` + `systemctl disable docker` |
| 3 | 清理 journald 历史日志 | 磁盘为主 | 中 | 先 `journalctl --disk-usage`（实测约 64MB）；`journalctl --vacuum-size=200M`。**如需留审计证据先导出** |
| 4 | 调小自建 Agent 空闲阈值（`IDLE_STOP_MS`） | 波动 | 中 | 属**配置变更**，需改 `team-console` 环境变量并重启；避开高负载时段 |
| 5 | 重启内存异常偏高的 hermes 网关 | 回到基线 | 中 | **重启前**备份该 profile 的 `SOUL.md` 与 `.env`；确认无 `running` 任务 |
| 6 | 重建 / 迁移到更大规格实例 | — | 高 | 走变更评审 |

```bash
docker ps                       # 动作 2 前置：期望无输出（本机实测无容器）
systemctl stop docker docker.socket; systemctl disable docker; free -m
journalctl --disk-usage; journalctl --vacuum-size=200M; journalctl --disk-usage    # 动作 3
# 动作 5 前置：确认没有正在跑的任务
node -e 'const{DatabaseSync}=require("node:sqlite");const d=new DatabaseSync("/opt/team-console/data/tasks.db",{readOnly:true});console.log(JSON.stringify(d.prepare("SELECT id,agent_id,started_at FROM tasks WHERE status=?").all("running"),null,1));d.close()'
```

> **不要**靠加 swap 文件「解决」OOM：轻量实例系统盘 IOPS 有限，大量换页会让 2 核 CPU 被 iowait 拖死，
> 表现为「机器还在但工作台卡到不可用」，比直接 OOM 更难排查。

### 10.2 花费怎么看 + 为什么叫「上界估算」
- 数据表 `usage_log`（`/opt/team-console/data/conversations.db`）；单价常量在 `server/src/config.js`（`PRICE_IN_PER_M` / `PRICE_OUT_PER_M` / `PRICE_CACHE_READ_PER_M`）。
- 快照与周报里的【本周花费】即读此表；`python3 /opt/team-console/ops/digest.py --cost-only` 可单独打印。
- **上界口径**：本系统按上游 `prompt_tokens` 全额计（未拆分其中缓存命中部分），而 Hermes 自身计费把缓存命中按 1/50 单价计 —— 故本表数字**偏高**，是花费上界。
- 精确对账看 Hermes：`/root/.hermes/profiles/<profile>/state.db` 的 `sessions` / `session_model_usage`（`estimated_cost_usd` 字段，源 `official_docs_snapshot`）。

### 10.3 登录必须走 HTTPS（Secure Cookie）
- **现象**：从 `http://IP:3000` 或 `http://127.0.0.1:8787` 打开工作台，登录后像「立刻变回未登录」。
- **原因**：登录 Cookie 带 `Secure`，浏览器在 http 下不回传 → 后端只能回 401。**这不是后端故障。**
- **正确入口**：`https://<域名或 IP>`（Caddy 443；自签证书属降级路径，需先信任证书）；本地调试可用隧道（如 ssh 端口转发到 443）。
- 决策依据：S4.0/B3「保持 Secure: true，不做 http 回退」；S4.1/C6-6 复述并写入本表。:3000 / 8787 是**本机诊断口**，不承担登录。

### 10.4 登出后旧 Cookie 应立即失效（token_version）
- 机制：`users.token_version` + JWT 内 `tv` 声明；**登出即 +1** → 该用户所有旧令牌立即 401「登录态已失效（已登出）」（服务端吊销，不再只是清本地 Cookie）。
- 管理员强制某成员下线（本机无 sqlite3 CLI，用 python3）：

```bash
python3 - <<'PY'
import sqlite3
c = sqlite3.connect('/opt/team-console/data/conversations.db')
c.execute("UPDATE users SET token_version = token_version + 1 WHERE username = ?", ('成员用户名',))
c.commit()
PY
```

### 10.5 长会话被裁剪（C3 上下文窗口）
- **现象**：Agent 回复里出现「更早的对话已省略；如需追溯请让对方复述关键结论」。
- **参数**：`CHAT_HISTORY_MAX_ROUNDS`（默认 12 轮，env 可配）；摘要模式默认**关**（`CHAT_SUMMARY_ENABLED=1` 打开，按 conversation+agent 缓存摘要）。
- **不会被裁**：任务上下文注入、D35 修正记录、@Agent 拉入的 `【上下文提示】` 片段（实现为标记白名单）。
- 收益量级：30 轮会话省 ~5.7%，120 轮省 ~26.8%（Agent 固定系统提示词约 17.4k tokens 是成本主项，故短会话省钱有限）。

### 10.6 产物校验（MANIFEST.json）
每个产物目录 `~/team-files/产出/<task_id>/` 内含 `MANIFEST.json`（文件名 + sha256 + 大小 + mtime），用于回滚/比对时校验「文件是否就是当时那一份」：

```bash
python3 - <<'PY'
import json, hashlib, os
d = '/root/team-files/产出/<task_id>'
doc = json.load(open(os.path.join(d, 'MANIFEST.json'), encoding='utf-8'))
for f in doc['files']:
    p = os.path.join(d, f['file'])
    print(('OK ' if hashlib.sha256(open(p,'rb').read()).hexdigest() == f['sha256'] else 'BAD'), f['file'])
PY
```

### 10.9 画像产物里的「旧对象名」为什么还在（勿删，属审计链）

**现象**：`~/team-files/系统通知/画像/画像-*.json` 的叙述里会出现**当前数据面已不存在**的名字，例如「阶段3上线检查清单」「校验-restricted-可选成员-正例」「testbot」「zhiban 会话 291」等（B8 数据清理后，`conversations/messages/tasks/memories` 均为 0，这些对象已不在库里）。

**结论：这是预期行为，请勿手工编辑或删除该文件。** 三条理由：

1. **它的证据源不是被清理的那个库。** 画像读的是 `/root/.hermes/` 下**各 Agent 的会话库（`profiles/*/state.db`）与看板 `kanban.db`** —— B8 的范围**明确不含** Hermes 侧（见《Session4.0-加固改进报告》§8.6-1）。因此画像统计到的「291 会话 / 10107 消息」是 Hermes 侧**真实发生过**的调用，不是脏数据。
2. **画像自己已经声明了口径。** 该文件的 `limitations[]` 与 `notable_discrepancies[]` 已逐条写明：工作台自研层「本轮复测仍然成立：均 0 行」、以及哪些计数是并发重复派发不宜读作工作量。**遇到疑似矛盾先读这两段**，多数"对不上"在其内部已被解释。
3. **它是 AI 产物的历史留痕。** 改写文本就等于**伪造 Agent 当时的输出**，会切断「触发 → 读取 → 产出」的可追溯性（C1-⑦、D15/D21 决策留痕都依赖这条链）。要更新口径就**重新生成一份**（`bash /opt/team-console/ops/run-job.sh profile`，产物按 mtime 取最新，旧文件自然退居历史），而**不是**回去改老的。

**排障动作**：怀疑画像数字与现状不符时 —— ① 先看该文件 mtime 是否早于最近一次清理/变更；② 再读它的 `limitations[]`；③ 需要当前口径就重跑一次 profile 生成新文件并与旧文件对比。**不要**用 live 库的计数去"纠正"历史画像的内容。

## 附录 C：已知隐患（实测）

> 以下均为本次核对中**实际观察到**的问题，按严重程度排序；第 1-3 条建议尽快处理。
> 本表只做记录与建议，**未做任何修复动作**。

| 编号 | 等级 | 隐患 | 影响 | 建议 |
|---|---|---|---|---|
| C-1 | 高 | 启动第二个 `team-console` 会被抢跑正在执行的任务 | `index.js` 里 `recoverStale({boot:true})` 与 `startSweeper()` 在 `app.listen` **之前**执行，而 `recoverOrphans()` 以**进程内** `running` 集合判断孤儿。第二实例（手工 `node src/index.js`、require 了 `tasks.js` 的诊断脚本、重复部署）启动瞬间 `running` 为空，会把所有 DB 标 `running` 的任务判为孤儿并重排队，随即 `pump` 开始执行 -> 同一任务被两个进程**同时执行、双写产物**；它随后才因 8787 占用退出，但抢跑已发生 | 排查脚本一律**只读**开库（`readOnly: true`），不要 require `tasks.js`；用 `pgrep -af "server/src/index.js"`（期望 1 行）确认单实例 |
| C-2 | 高 | 自建 Agent 端口分配不检查主机实际占用 | `registry.js` 的 `allocatePort(reg)` 只用 `agents.json` 里已登记的 `port` 构造 `used` 集合，从 8650 向上取第一个未被**登记**的端口，**不做任何 bind / ss 探测**。当某端口被未登记进程占用时，新建 Agent 仍会被分配该端口：注册表已写、单元已装，但首次唤醒必然失败 | 分配前做真实可用性探测（`net.createServer().listen(port)` 试探后关闭），或分配后立刻 `probe()` 校验 |
| C-3 | 中 | 通知「首次登录炸历史」 | `notify.ts` 的 `tick()` 把 `primed = true` 写在 `try/catch` **之外**，而 `main.ts` 在含登录页的启动阶段就调用 `startNotify(4000)`；未登录时 `/api/poll` 返回 401（线上日志确有 `401 /api/poll?since=0`），catch 不更新 `since` 但 `primed` 已被置位；且 `resetNotify()` **只在退出登录时**调用。**先看登录页再登录**的用户，登录后首次成功轮询会以 `since=0` 拉回全部历史通知：未读角标等于历史文件数，并弹最多 3 条旧文件桌面通知 | 把 `primed = true` 移入 `try` 成功分支（或首轮 `since===0` 时只建基线并 return），并在登录成功后调用 `resetNotify()` |
| C-4 | 中 | 没有 OOM 兜底，也没有任何 cgroup 内存上限 | `systemd-oomd` 未安装（实测 `Unit ... could not be found`）；`MemoryMax=infinity`。内存耗尽时由**全局内核 OOM killer** 按 `oom_score` 挑进程杀，可能杀掉 `team-console` 或某个 hermes 网关而非最占内存者；叠加 C-7 会形成「被杀 -> 重启 -> 再被杀」循环 | 为关键单元设 `MemoryMax` / `MemoryHigh` 做软着陆，或安装 `systemd-oomd`（需配合压力策略，否则也会误杀） |
| C-5 | 中 | `team-console` 以 root 运行且无任何 systemd 沙箱 | 单元为 `User=root` `Group=root`，且 `ProtectSystem=no`、`ProtectHome=no`、`PrivateTmp=no`、`NoNewPrivileges=no`（实测）。Node 进程一旦被利用即为 root 全权限；`ProtectHome=no` 意味着可读写 `/root` 下的 `team-files` 与 `.hermes`（含各 profile 密钥） | 至少加 `NoNewPrivileges=yes`、`PrivateTmp=yes`、`ProtectSystem=strict` 并配 `ReadWritePaths=/opt/team-console/data /root/team-files`（需先验证功能，属高风险管理变更） |
| C-6 | 中 | 数据库与日志文件权限为 644，本机其它用户可读 | `data/` 目录 755，三个库及其 `-wal`/`-shm` 均为 `644 root:root`；`/var/log/caddy/cloudloom-access.log` 为 `644 caddy:caddy`。本机存在可登录的 `ubuntu`(1000) 与 `lighthouse`(1001)（`/etc/passwd` 实测）。这两个账号可读全部聊天记录、任务内容与**用户口令散列**（scrypt），以及访问日志中的 URI 与来源 IP。作为对照，`agents.json`、`server/.env`、`files.json` 均为 600（正确） | `chmod 600 /opt/team-console/data/*.db*`（服务以 root 运行不受影响），并为 Caddy 访问日志收紧权限或加轮转 |
| C-7 | 中 | 单元无限重启，崩溃时会打满 2 核 CPU | `team-console` 与所有 `hermes-gateway-*` 均为 `Restart=always` + `StartLimitIntervalSec=0`（无速率限制）。进程若能起来但立刻崩，会以 `RestartSec=3`/`5` 无限循环，在 2C4G 上迅速吃满 CPU 并刷爆 journald | 出问题时**先 `systemctl stop` 止血再排查**，不要反复 `restart`；为单元设合理的 `StartLimitBurst` / `StartLimitIntervalSec` |
| C-8 | 中 | 手工 `hermes gateway run` 会与 systemd 单元抢同一端口 | 核对 `journalctl -u hermes-gateway-cehua` 时看到同一 profile 先后出现不同 PID（`python[27602]` 与 `python[907]`），而 `NRestarts=0` —— 说明 `27602` 不是 systemd 重启产生，而是**手工启动**的额外实例，两者 `API_SERVER_PORT` 均为 8642。后果是「systemd 认为自己在跑、实际监听的是另一个进程」，停单元也杀不掉真正占端口的进程 | 启动 / 停止一律走 `hermes -p <id> gateway start\|stop`（经 systemd）或 `systemctl start\|stop hermes-gateway-<id>`；**禁止** `hermes -p <id> gateway run`。自查：`for p in cehua chengxu pingshen zhiban testbot; do printf "%-10s %s\n" "$p" "$(pgrep -c -f "profile $p")"; done`（每个应为 1） |
| C-9 | 低 | 端口 3000 上的静态服务是冗余的 | `config.js` 的 `STATIC_PORT = 3000`，`index.js` 仍启动第二个 Express 监听；但 Caddyfile 已改为 `root * .../dist` + `file_server` **直出**，不再回源 3000（Caddyfile 注释亦写明「不再依赖 :3000 静态服务」）。多一个监听端口与一份代码路径，容易让排查者误判「页面来自 3000」 | 确认无外部依赖后移除该监听（属**代码变更**）；在此之前以 443 的实际行为为准 |
| C-10 | 低 | `tc_token` Cookie 未设置 `Secure` 属性 | `auth.js` 的 `setCookie()` 只设了 `httpOnly` / `sameSite=lax` / `path=/` / `maxAge`，**未设 `secure: true`**。在 https 页面上该 Cookie 也可能通过明文 http 请求发送；配合 `:80` 到 `:443` 的跳转，存在被降级利用的理论空间 | 加 `secure: true`（当前所有访问都走 `:443`，满足前提） |
| C-11 | 低 | Caddy 访问日志无轮转 | Caddyfile 的 `log` 段只写了 `output file /var/log/caddy/cloudloom-access.log`，没有 `roll_size` / `roll_keep`；实测约 1.1 MB 且在增长 | 在 `log` 段加 `roll_size 50MiB` 与 `roll_keep 5`，或引入 `logrotate` |
| C-12 | 低 | SPA fallback 会「吞掉」未知路径，与真实 404 难以区分 | Caddyfile 兜底 `handle` 用 `try_files {path} /index.html`，即除 `/api/*` 与 `/mcp*` 外任何路径都返回 `index.html`（200）。排查「下载 404」时容易困惑 —— 只有 `/api/*` 前缀下才会得到真正的 JSON 404（如 `404 条目不存在`）；静态资源缺失时才会命中后端 503 兜底文案 | 排查以 `/api/*` 的返回为准；静态资源问题看 `/assets/` 路径与 Caddy 访问日志状态码 |

## 附录 E：系统重启后的任务恢复（S4.0 / B5-① 新增，实测）

**现象**：服务器或 team-console 重启时，正在执行的任务会被打断。系统会自动恢复（重新排队继续执行），
因此**重启后无需人工干预**；但恢复意味着**重试可能与中断前重复执行**，必须知道去哪里看、以及产物会不会被覆盖。

| 你会看到什么 | 在哪里看 | 说明 |
| --- | --- | --- |
| 任务进度显示「系统重启后恢复（可能与中断前重复执行）」 | 任务 Tab → 任务卡片进度 | 该标注在重试执行期间持续可见，直到本次执行结束 |
| 一条「任务已从系统重启中恢复」通知 | 工作台通知中心（顶部铃铛） | 文件落地在 `~/team-files/系统通知/任务恢复-<YYYYMMDD-HHMMSS>.md`，含恢复时间、来源、任务列表 |
| 服务日志 `[tasks] 中断恢复：N 个任务重新排队` | `journalctl -u team-console` | 「启动恢复」为重启时即刻回收（30 秒宽限）；「孤儿任务自动重排」为 60 秒巡检兜底 |
| 中断前已产出的文件**仍在**，内容不变 | `~/team-files/产出/<task_id>/` | 恢复时会把中断前已有文件名记入任务 meta，并在指令中要求 Agent 严禁覆盖 |

**不覆盖规则（重试时）**：产物目录固定 `~/team-files/产出/<task_id>/`。若目标文件名与中断前已有文件同名，
必须另存为 `<原名>-retry-<HHMMSS>`（例：`报告.md` → `报告-retry-181230.md`），**绝不覆盖**既有文件。
该规则由服务端在任务指令中强制注入（重试任务带【重试约束】段）。

**验证要点（可复现）**：构造一个 `status=running` 且 `started_at` 早于 30 秒的任务行 → `systemctl restart team-console`
→ 观察任务回到队列并以「系统重启后恢复…」标注继续执行、通知中心出现恢复通知、产物目录中既有文件 sha256 不变。

**注意**：服务端不复制中断前文件（不做字节级快照）。不覆盖由「指令强约束 + 恢复时清单留痕 + 通知可见」保证；
若需硬性兜底，需二期增加产物快照还原。
